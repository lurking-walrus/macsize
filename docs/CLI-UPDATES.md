# Updating the CLI

Release builds of `macsize` check for new versions in the background and tell you when one is
available. They never replace themselves without being asked: you run `macsize update`.

## The notice

After a normal command (`scan`, `largest`, `types`, `bench`) finishes, you may see one line on
stderr:

```
A new version of macsize is available: 0.1.0 → 0.2.0. Run `macsize update` to install.
```

- At most one network check per 24 hours. The result is cached in
  `~/Library/Caches/macsize/update-check.json` (or `$XDG_CACHE_HOME/macsize/` if that's set).
- The check runs alongside your command. At exit macsize waits at most about 300 ms for it, and
  otherwise falls back to what the cache already knows. Network errors are ignored.
- The notice is only shown when stderr is a terminal. It's never shown with `--json`, for
  `help`/`version`, when `CI` is set, or when `MACSIZE_NO_UPDATE_NOTIFIER` is set to a non-empty
  value.
- Source builds (`swift build`, `scripts/install.sh`) have no release URL compiled in, so they never
  check.

## `macsize update`

```
macsize update           # install the latest release
macsize update --check   # only report whether a newer version exists
```

What it does depends on how macsize was installed. This is detected from the real path of the
executable, so a symlink on your PATH counts as whatever it points to.

| Install | Detected by | `macsize update` |
| --- | --- | --- |
| Inside MacSize.app | `….app/Contents/Helpers/macsize` | Explains that the app updates its CLI and opens MacSize; choose **MacSize › Check for Updates…** |
| Homebrew | path contains `/Cellar/` or `/Caskroom/`, or is under `/opt/homebrew` | Refuses and tells you to run `brew upgrade macsize` |
| Standalone binary | anything else | Downloads, verifies and replaces the binary in place |

For a standalone binary, it:

1. Fetches `<release base URL>/latest.json`. If that version isn't newer, it prints
   `macsize X is up to date`.
2. Downloads the `macsize-X.Y.Z-macos-universal.tar.gz` tarball into a temporary directory next to
   the binary (on the same volume, so the final swap is atomic). If that directory isn't writable,
   for example `/usr/local/bin`, run `sudo macsize update`.
3. Checks the tarball's SHA-256 and its Ed25519 signature against the public key built into the
   release. It refuses to update if either check fails, or if the build has no key.
4. Extracts it with `/usr/bin/tar`, runs the new binary's `--version` to confirm it reports the
   expected version, and then `rename()`s it over the current executable with mode 0755.

## Development: testing against a local server

Debug builds (`swift build`, not `-c release`) read two environment overrides. They're compiled
out of release builds.

- `MACSIZE_UPDATE_BASE_URL` is used in place of `BuildInfo.releaseBaseURL`.
- `MACSIZE_UPDATE_PUBLIC_ED_KEY` is used in place of `BuildInfo.updatePublicEDKey`, as a base64 raw
  Ed25519 public key.

```sh
mkdir -p /tmp/fake-release && cd /tmp/fake-release
cat > latest.json <<'EOF'
{"version":"9.9.9","build":"1","published_at":"2026-01-01T00:00:00Z",
 "cli":{"url":"http://127.0.0.1:8000/macsize-9.9.9-macos-universal.tar.gz","sha256":"00","ed_signature":""},
 "app":{"url":"http://127.0.0.1:8000/MacSize-9.9.9.zip"}}
EOF
python3 -m http.server 8000 --bind 127.0.0.1 &

# Use a throwaway cache so the 24h throttle doesn't get in the way.
export MACSIZE_UPDATE_BASE_URL=http://127.0.0.1:8000 XDG_CACHE_HOME=/tmp/fake-release/cache
swift run macsize -- -d 1 ~/Downloads   # prints the notice on stderr
swift run macsize -- update --check
```

To exercise a full install, build a tarball that holds a single `macsize` (a shell script that
prints `macsize 9.9.9` is enough). Sign it with a key generated by CryptoKit
(`Curve25519.Signing.PrivateKey`), fill in `sha256` and `ed_signature`, and run a copy of the debug
binary from a scratch directory with `MACSIZE_UPDATE_PUBLIC_ED_KEY` set. `macsize update` replaces
whichever binary is running, so don't run it from `.build/`.
